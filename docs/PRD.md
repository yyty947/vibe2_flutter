## 1. 产品概述

### 1.1 产品定位

一款以"大厂前端生存"为主题的 Android 移动端文字资源管理游戏。玩家扮演一名互联网大厂P6/T3级别的前端开发，在"降本增效"的压力下，通过30天的资源管理与抉择，尝试在裁员危机中生存下来。

**产品关键词：**
- 文字驱动
- 资源管理
- 职场生存模拟
- 多结局分支
- 赛博朋克终端风格沉浸体验

### 1.2 背景故事

2026年，你是一名某互联网大厂的前端开发。公司高管频繁强调"降本增效"，你所在的业务线数据惨淡，部门被"优化（裁员）"的传闻甚嚣尘上。距离最终的"审判日（财报发布）"还有30天。

### 1.3 核心目标

在30天内存活下来，并达成最优结局。单局游玩时长约20-40分钟。

## 2. 产品目标

### 2.1 目标

- 提供完整的核心游戏循环：行动选择 → 随机事件 → 日结清算
- 实现5种不同结局，让玩家有多周目探索动力
- 通过赛博朋克终端视觉风格营造高压职场沉浸式体验
- 支持游戏进度本地自动保存，无需账号系统
- 单局时长控制在20-40分钟，适合碎片时间游玩

### 2.2 非目标

当前版本明确不做：
- 用户账号系统、在线登录
- 后端API、云端同步
- 多人在线/实时协作
- ~~复杂的技能树或角色成长系统~~ **已在 v1.3.0 实现**
- 付费系统或内购
- ~~移动端触摸优化~~ **已实现**（横屏锁定 Android APK，触觉反馈）
- ~~开场视频~~ **已实现**（Patch-F16：NEW GAME 全屏视频 + 1000ms 淡入淡出 + 点击跳过）
- ~~小游戏玩法~~ **已实现**（Patch-F17：QTE「CSS 绝对居中」快速反应事件，融入事件系统）

## 3. 目标用户

### 3.1 核心用户

- 互联网从业者（程序员、产品经理、设计师）
- 对职场生存题材感兴趣的玩家
- 喜欢资源管理和文字冒险类游戏的玩家

### 3.2 用户诉求

- 体验职场高压环境下的决策压力
- 通过多周目探索不同结局
- 享受文字叙事和随机事件带来的不确定性
- 在碎片化时间内完成一局游戏
- 无需注册即可快速开始游戏

## 4. 核心使用场景

### 4.1 新手探索

用户首次进入游戏，通过标题画面了解背景设定，开始第一局游戏，学习基础操作（选择行动、处理事件、理解状态系统）。

### 4.2 多周目挑战

用户已通关一次，尝试不同的策略组合（纯内卷路线、跳槽准备路线、平衡发展路线），探索不同结局。

### 4.3 中断续玩

用户游戏进行到中途需要离开，关闭应用或切到后台后再次打开，从自动保存的进度继续游戏。

## 5. 核心机制与玩法设计

*目标：本章节定义游戏所有状态及流转规则。开发过程中，凡涉及数值计算、流程控制的逻辑，必须严格遵循本章节的约束，严禁自行扩展未定义的机制。*

### 5.1 核心状态字典 (Global State)

游戏由以下四个核心资源数值驱动，所有数值必须遵循 **[0, 100] 的硬性边界限制（Clamp）**，不可溢出或跌穿。

| 状态项 | 初始值 | 每日自然衰减 | 获取途径 | 失去途径 | 极值惩罚/奖励 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **精力 (Energy)** | 75 | -5 (每日结算时) | "带薪拉屎"行动 (+20)<br>特定休息类事件 | 工作类行动 (-10 ~ -20)<br>加班类事件 | **降至 0：立即触发"猝死/进ICU" Bad Ending。** |
| **绩效 (KPI)** | 50 | 0 | "写代码/修Bug"行动 (+5 ~ +15)<br>完成需求类事件 | 摸鱼被抓事件<br>背锅类事件 | **降至 0 或 30天结算时 < 20：触发"绩效垫底" Bad Ending。** |
| **面试准备度 (Interview)**| 10 | 0 | "刷八股文"行动 (+8)<br>自我提升类事件 | 极少下降（除非被 HR 发现并警告） | **≥ 80：在每日结算阶段触发"提前拿到 Offer" Good Ending。** |
| **老板怀疑度 (Suspicion)**| 20 | 0 | "刷八股文"行动 (+5)<br>"带薪拉屎"行动 (+3)<br>拒绝加班/甩锅事件 | "写代码"行动 (-2)<br>主动背锅/表忠心事件 | **≥ 70：增加高危负面事件触发概率。不直接致死。** |

**状态边界规则：**
- 所有数值严格限制在 `[0, 100]` 区间
- 任何计算结果小于0时强制设为0，大于100时强制设为100
- 精力值每日结算时额外衰减 -5（已在"每日自然衰减"列体现）

### 5.2 核心时间轴与日历系统

**总时长：** 固定为30天。起始为 Day 1，上限为 Day 30。

**每日结构 (Day Phase)：**
- 每天被划分为两个行动点（Action Points）：**上午 (Morning)** 和 **下午 (Afternoon)**
- 初始阶段为上午
- 执行一次行动后，上午变为下午
- 执行第二次行动后，进入事件阶段

### 5.3 行动指令系统 (Action System)

玩家在"上午"和"下午"阶段必须从动态抽取的4个行动中选择一项执行。行动池包含12个行动（4核心 + 8条件）���通过 `sampleActionPool()` 算法确保每轮抽取的行动组合合理。执行动作后，直接产生数值变化，并进入下一阶段。

> **注**：MVP 阶段仅有 4 个核心行动。v1.3.0 通过 Patch-F05 扩充至 12 个，含条件行动和技能解锁行动。完整清单见 GAME_CONTENT §1。

#### 可选行动清单

| 行动名称 | 精力变化 | KPI变化 | 面试度变化 | 怀疑度变化 | 前置约束 | 反馈文本示例 |
|---------|---------|---------|-----------|-----------|---------|-------------|
| **写业务代码** | -10 | +5 | 0 | -2 | 无 | `[COMMIT] 提交了3个PR，绩效微升，老板觉得你很安分。` |
| **修屎山Bug** | -20 | +15 | 0 | 0 | 精力必须 > 20 | `[BUGFIX] 解决了陈年老Bug，虽然心力交瘁，但在周报上大放异彩。` |
| **偷偷刷八股文** | -10 | 0 | +8 | +5 | 无 | `[STUDY] 刷了5道Hard题。你频繁切屏引起了主管的注意。` |
| **带薪拉屎** | +20 | 0 | 0 | +3 | 无 | `[SLACK] 在厕所隔间冥想了半小时，血条恢复了！` |

**前置约束说明：**
- "修屎山Bug"行动有硬性前置条件：当前精力必须 > 20
- 若精力 ≤ 20，该行动按钮置灰，显示提示"精力不足，强行修Bug会进ICU"
- 其他行动无前置约束，即使精力不足也可执行（但可能触发BE）

> **Flutter 实现**: 行动数据位于 `assets/data/actions.json`，运行时由 `lib/data/game_data.dart` 加载为 `ActionDef` 类，通过 `lib/logic/action_pool.dart` 的 `sampleActionPool()` 动态抽取，效果修正链由 `lib/logic/action_resolver.dart` 的 `resolveActionEffects()` 处理。

### 5.4 事件触发与结算流程 (Event & Settlement Loop)

**流程状态机（必须严格遵循）：**

```
Day N 开始 → 显示开场白 → 上午行动 → 下午行动 → 触发随机事件 → 日结清算 → Day N+1
```

**详细流程规则：**

1. **开场白阶段**
   - 每天开始时显示当日开场白文本（30段，每天一段）
   - 开场白使用打字机效果逐字显示
   - 玩家可点击或按 Escape 跳过
   - 开场白不影响任何数值

2. **上午行动**
   - 玩家点击行动按钮
   - 立即应用该行动的数值变化
   - 在终端区打印行动反馈日志
   - 状态变更为"下午"
   - 玩家继续选择第二次行动

   > **注（v1.3.0 扩展）**：上午行动后有 25% 概率触发"打断事件"（Patch-F01），打断消耗下午行动点。行动效果还受连选惩罚（Patch-F04）、即时抓包（Patch-F04）、日间修饰符（Patch-F01）、状态条件（Patch-F03）、技能被动（Patch-F05）等多层修正。

3. **下午行动**
   - 玩家点击行动按钮
   - 立即应用该行动的数值变化
   - 在终端区打印行动反馈日志
   - **触发随机事件**（进入事件阶段）

4. **随机事件处理**
   - 系统从事件库中抽取**1个**事件
   - 抽取规则：先过滤满足触发条件的事件 → 按权重加权随机 → 10%概率不触发事件
   - 已触发过的事件在后续天数中权重降低50%
   - 弹出事件对话框，包含标题、描述、2个选项(A/B)
   - 玩家选择选项后，立即应用选项对应的数值变化
   - 在终端区打印选项反馈日志
   - 进入日结清算阶段

5. **日结清算 (End of Day Settlement)**
   - 应用每日自然消耗：精力 = 精力 - 5
   - **执行中断检查（按优先级）：**
     - 检查1：当前精力 ≤ 0？是 → 立即触发 BE（精力耗尽）
     - 检查2：当前绩效 ≤ 0？是 → 立即触发 BE（绩效垫底）
     - 检查3：当前面试度 ≥ 80 且 怀疑度 < 85？是 → 立即触发 Good Ending（成功跳槽）（Patch-F02 新增怀疑度门槛）
   - 若未触发任何结局：
     - 天数加一（Day N → Day N+1）
     - 重置阶段为"上午"，清除当日修饰符
     - 周度成长点结算（Day 7/14/21 时弹出周度复盘UI）
     - 执行本地自动保存
     - 播放天数过渡动画
     - 进入下一天的开场白阶段

6. **最终审判 (Day 30)**
   - 当进入 Day 30 的日结清算时，若未触发提前结局，执行最终结局判定
   - **结局优先级（从高到低）：**
     1. 内卷之王：KPI ≥ 80 且 怀疑度 < 30 且 精力 ≥ 20
     2. 成功跳槽：面试度 ≥ 60 且 怀疑度 < 70
     3. 和平分手：KPI ≥ 30 且 怀疑度 < 70 且 精力 > 0
     4. 绩效垫底：以上都不满足

### 5.5 结局系统

**结局清单与触发条件：**

| 结局名称 | 类型 | 触发时机 | 触发条件 |
|---------|------|---------|---------|
| **精力耗尽** | Bad Ending | 日结清算（即时） | 精力 ≤ 0 |
| **绩效垫底** | Bad Ending | 日结清算（即时或Day 30） | 绩效 ≤ 0（即时）<br>或 Day 30 时优先级兜底（见 DOC_AUDIT Patch-011） |
| **成功跳槽** | Good Ending | 日结清算（可提前） | 面试度 ≥ 80 且 怀疑度 < 85（即时触发）<br>或 Day 30时面试度 ≥ 60 且 怀疑度 < 70 |
| **和平分手** | Normal Ending | Day 30结算 | KPI ≥ 30 且 怀疑度 < 70 且 精力 > 0 |
| **内卷之王** | Best Ending | Day 30结算 | KPI ≥ 80 且 怀疑度 < 30 且 精力 ≥ 20 |

**结局判定规则：**
- 精力归零和绩效归零的BE在日结阶段立即触发，不等待Day 30
- 面试度≥80的成功跳槽在日结阶段立即触发，不要求活满30天
- Day 30结算时按上述优先级顺序判定，只触发一个结局
- 游戏结束后自动清除存档，玩家可选择重新开始

## 6. 事件系统

### 6.1 事件设计原则

事件是游戏叙事的核心载体，必须遵循以下设计原则：

**代入感优先：**
- 使用第二人称"你"，让玩家身临其境
- 基于真实职场场景，避免过于戏剧化
- 通过具体细节（飞书消息、会议室争吵、凌晨钉钉）营造氛围

**选择的两难性：**
- 每个事件必须提供2个选项
- 选项之间没有绝对的最优解，各有利弊
- 高风险选项可能带来高回报，也可能加速BE
- 保守选项稳定但收益有限

**数值影响的合理性：**
- 事件对状态的影响必须符合逻辑
- 加班类事件消耗精力但提升KPI
- 摸鱼类事件增加怀疑度但可能提升面试度
- 重大危机事件可能造成多维度影响

### 6.2 事件主题分类

事件应覆盖以下6个主题领域，确保游戏体验的多样性：

| 主题领域 | 典型场景 | 设计目标 |
|---------|---------|---------|
| **产品需求** | 需求变更、五彩斑斓的黑、紧急插单 | 体现互联网行业的需求不确定性 |
| **人际关系** | HR约谈、同事甩锅、团建活动、办公室政治 | 展现职场社交的复杂性 |
| **技术事故** | 线上Bug、代码Review、技术债务、架构调整 | 反映技术工作的真实压力 |
| **职场八卦** | 裁员传闻、同事离职、内部消息、组织调整 | 营造危机四伏的氛围 |
| **自我提升** | 刷八股文、副业机会、猎头联系、技能学习 | 提供跳槽准备的路径 |
| **生存危机** | 体检报告、绩效评估、奖金缩水、领导约谈 | 直接威胁生存的高风险事件 |

### 6.3 事件触发机制

**触发时机：**
- 每天下午行动完成后触发（每天仅一次）
- 10%概率不触发任何事件（让玩家喘息）

**触发条件：**
- 部分事件需要满足前置条件才会出现（如：第10天后、怀疑度>70等）
- 条件应基于游戏状态动态判断

**触发频率控制：**
- 高频事件：日常性、低风险（如：需求变更、普通会议）
- 中频事件：阶段性、中等风险（如：绩效评估、项目上线）
- 低频事件：稀有、高风险高回报（如：领导离职、裁员实锤）
- 已触发过的事件后续出现概率降低

### 6.4 事件内容要求

**数量要求：**
- MVP版本至少20个不同事件 — **已实现65个**（EV_001-EV_065），含14个高危事件与5个QTE事件
- 建议分布：产品需求类5-8个、人际关系类5-8个、其他类别各2-5个 — **实际分为4大类**（日常搬砖、职场暗流、技术危机、个人突围），见 `event-categories.json`

**结构要求：**
- 每个事件包含：标题、描述、2个选项
- 每个选项包含：选项文本、状态变化、结果反馈
- 描述文本控制在200字以内，保持节奏紧凑

**叙事节奏：**
- Day 1-10：以铺垫为主，氛围轻松但暗示危机
- Day 11-20：压力渐增，同事开始消失，传闻实锤
- Day 21-30：高压阶段，生存抉择，终局氛围

## 7. 视觉与氛围设计

### 7.1 视觉风格定位

**核心风格：** 程序员熟悉的开发环境
- 参考 赛博朋克终端/CRT 显示器风格
- 使用等宽字体，营造代码编辑器氛围
- 整体色调偏暗，高对比度文字确保可读性

**配色原则：**
- 背景色：深色（接近纯黑或深灰），减少视觉疲劳
- 状态指示：使用绿（正面）、黄（警告）、红（危险）三色体系
- 代码高亮：使用程序员熟悉的语法高亮配色（关键字、字符串、注释等）
- 保持克制，避免过多颜色分散注意力

### 7.2 界面布局原则

**信息架构：**
- **顶部区域：** 显示游戏进度（当前天数/总天数），提供设置入口
- **左侧区域：** 状态面板，实时显示四大核心指标（精力、KPI、面试度、怀疑度）
- **中央区域：** 主要内容区，显示开场白、事件、行动选项
- **底部区域：** 终端日志区，滚动显示游戏反馈信息

**交互设计：**
- 按钮和选项清晰可点击
- 当前不可用的行动需要明确标识（如精力不足时"修Bug"置灰）
- 状态变化需要即时视觉反馈

### 7.3 氛围营造要素

**压力可视化：**
- 当精力或KPI低于20时，界面应通过视觉手段传递紧张感
- 可考虑的方案：红色边框闪烁、背景色温变化、心跳呼吸灯效果等
- 危险状态下的视觉反馈应逐渐增强，而非突兀出现

**叙事沉浸：**
- 文字内容使用打字机效果逐字显示，增强叙事感
- 支持玩家主动跳过（点击或按键），避免等待烦躁
- BE触发时使用故障艺术（Glitch）效果，强化终结感

**反馈明确：**
- 玩家操作后，终端区立即显示反馈日志
- 状态值变化使用颜色区分（上升绿色、下降红色）
- 重大事件（如结局触发）需要显著视觉标识

## 8. 音频设计

### 8.1 音频设计原则

**功能优先：**
- 音效应服务于游戏反馈，增强操作确认感
- 不同类型的反馈（成功、警告、危险）需要明显区分的听觉提示
- 避免过度使用音效造成干扰

**氛围营造：**
- BGM应与游戏状态同步变化，强化情绪体验
- 日常状态使用轻松、不干扰的背景音乐
- 危机状态（如精力过低）音乐应变得紧张不和谐
- 结局音乐需要匹配结局情感色彩（好结局温暖、BE结局压抑）

### 8.2 音效需求分类

**交互音效：**
- 按钮点击确认音
- 行动执行反馈音
- 选项选择确认音

**状态反馈音效：**
- 状态值上升提示（积极、清脆）
- 状态值下降提示（低沉、警示）
- 危险状态警告（循环心跳声或警报声）

**事件音效：**
- 随机事件弹出提示（引起注意但不突兀）
- 重大事件特殊音效

**结局音效：**
- Bad Ending：不和谐、故障风格音效
- Good Ending：温暖、解脱风格音乐

### 8.3 背景音乐场景需求

| 场景 | 音乐需求 |
|------|---------|
| **主界面/日常** | 轻松、低频、不干扰阅读决策 |
| **事件触发** | 紧张感提升，与日常形成对比 |
| **危险状态** | 不和谐、压迫感，提示玩家处境危险 |
| **好结局** | 温暖、正向、解脱感 |
| **坏结局** | 沉重、压抑、遗憾感 |

### 8.4 音频技术要求

- 提供全局静音开关，玩家可随时关闭所有音频
- 支持独立调节BGM和音效音量
- 音频资源应懒加载，不影响首屏加载速度
- 优先使用无版权争议的音频资源

## 9. 自动保存系统

### 9.1 存储方案

- **Flutter 版**: `SharedPreferences` key `frontend-survival-save`（实现于 `lib/services/save_service.dart`）
- **触发时机：** 无结局日结进入下一天 `OPENING` 后，由 `GameScreen` post-frame 自动保存
- **存档大小：** < 10KB

### 9.2 存档内容

存档需要保存玩家进度所需的核心数据：
- 游戏版本（用于兼容性处理）
- 当前天数和阶段
- 四个核心状态值（精力、KPI、面试度、怀疑度）
- 已发生的事件记录（用于控制重复触发）
- 玩家的行动历史统计
- 存档时间戳

### 9.3 存档行为

1. 无结局日结进入下一天 `OPENING` 后自动保存，无需手动操作
2. 应用重新打开后，检测存档并提示是否继续上次进度
3. 游戏结束后（任何结局），`EndingScreen` 在结局演出完成后自动清除存档
4. 提供"重新开始"按钮，重置内存状态并回到标题画面

## Current Implementation Reconciliation (2026-05-30)

This section is authoritative for the current shipped Flutter behavior and supersedes older historical wording elsewhere in this PRD.

- Product/platform: Android Flutter game, landscape only, pure client-side. Launcher label is `Frontend Survival`.
- Version: app package version is `2.0.0+2`; save compatibility version is `GameState.gameVersion == 2.0.0`.
- Runtime flow: NEW GAME shows the full-screen intro video first; CONTINUE skips the video and enters the saved `OPENING` phase.
- State model: current `GameState` has 24 fields. `showIntroVideo` is transient UI state and is not serialized.
- Static content scale: 12 actions, 65 events, 14 high-risk events, 5 QTE events, 30 openings, and 5 endings.
- Event rules: every event JSON entry still has exactly two options. QTE events also include `qteConfig`; their QTE result effects come from `qteConfig`, not from the fallback A/B options.
- QTE schedule: fixed QTE days are Day 5, 10, 15, 20, and 25. Week review days are Day 7, 14, and 21, so there is currently no overlapping conflict day.
- Day 30 ending priority: settlement applies daily energy drain, runs `checkDailyEnding()` on all days including Day 30, then runs final judgment only if no daily ending occurred. Final GE_OFFER requires interview >= 60 and suspicion < 70.
- Save behavior: no-ending settlement moves to the next `OPENING`; `GameScreen` then saves post-frame. Ending save clear happens in `EndingScreen` after the glitch/reveal animation completes.
- Content separation: ending title/text are read from `assets/data/endings.json` through `GameData.endings`.
- Testing baseline: `flutter analyze` returns zero issues; `flutter test` passes 248 tests across 15 Dart test files.
